# Trajectory Compaction: 2026-07-16 - 2026-07-16

## Summary

A single short session (~2 minutes, one lead agent) on branch `fix/pty-injection-exit-race` closed a race in the Rust broker's PTY worker where Relay parsed its own injected text as agent-issued commands. The PTY read loop in `crates/broker/src/pty_worker.rs` scans decoded terminal output for two command classes: a bare `/exit` line, and `KIND:` continuity headers. Both scans were guarded only by `pending_verifications.is_empty()`. That guard is insufficient because paced injection writes characters to the PTY and the terminal echoes them back _before_ the post-write `PendingVerification` entry is queued. During that window the guard reads as "nothing pending, safe to parse," so Relay saw its own echoed `/exit` and killed the agent — visibly, a freshly spawned PTY agent terminating before its initial task was ever delivered. The fix introduces a small pure predicate, `injected_output_command_detection_allowed(active_injection_present: bool, pending_verifications_present: bool) -> bool`, returning `!active_injection_present && !pending_verifications_present`. Both call sites in `run_pty_worker` (the `/exit` line scan around line 1047 and the continuity-buffer append around line 1103) now call it with `(active_injection.is_some(), !pending_verifications.is_empty())`. Widening the guard from "verification pending" to "anywhere in the injection lifecycle" closes the echo-before-verification gap. A doc comment on the predicate states the invariant — detection stays disabled for the _entire_ injection lifecycle — rather than restating the code. Coverage is a truth-table unit test, `injected_output_commands_are_suppressed_through_injection_lifecycle`, in the existing `#[cfg(test)] mod tests` block, asserting all four input combinations (only `(false, false)` permits detection). A one-line `### Fixed` bullet was added to `[Unreleased]` in `CHANGELOG.md`, impact-first and naming `agent-relay-broker`. The change is 28 lines across one Rust file plus the changelog. The compaction ran before the commit landed (so `trail` recorded no commits at that moment); the work was then committed as `4764e65` ("fix(broker): ignore commands echoed during injection") on `fix/pty-injection-exit-race` and opened as PR #1288.

## Conventions Established

- **Extract decision logic out of the `tokio::select!` loop into pure `fn(bool, ...) -> bool` predicates or policy enums, then unit-test them exhaustively via truth tables in the file's `#[cfg(test)] mod tests`.**: The select-loop body mixes I/O, frame sending, and verification side effects, making it costly to test directly. Pure predicates are exhaustively testable in microseconds and prevent the two call sites from drifting apart. (scope: `crates/broker/src/pty_worker.rs` and comparable broker hot loops; established prior art is `injection_pop_allowed` and the ack-resolution policy type.)
- **When a boolean guard encodes a timing invariant, document the invariant and the failure window in a doc comment on the predicate — not the mechanics of the expression.**: `!a && !b` is self-evident; that echo can arrive before verification is queued is not, and is exactly what a future reader would otherwise re-break. (scope: Rust guards in `crates/broker/`.)
- **Guard PTY-output command detection on the whole injection lifecycle, never on a single downstream signal such as `pending_verifications`.**: Relay writes to the same PTY it reads from; anything it injects comes back as output. Any narrower guard reintroduces self-parsing races. (scope: Any new command/marker detection added to the `run_pty_worker` read path.)
- **Pair each user-visible broker fix with one impact-first `### Fixed` bullet under `[Unreleased]` naming the binary (`agent-relay-broker`) and the practical effect.**: Repo changelog policy in `CLAUDE.md`: concise, impact-first, no PR links or implementation backstory. (scope: `CHANGELOG.md` at repo root.)

## Lessons Learned

- A guard that keys off a _downstream_ signal of an operation cannot cover the operation's startup window. `pending_verifications` is populated after the paced write, so it was blind precisely when echo arrives. (The original `/exit` and `KIND:` guards used `pending_verifications.is_empty()`, which looks like "no injection activity" but actually means "no injection has reached verification yet.") - When guarding against self-inflicted input, gate on the earliest state that marks the operation as begun (`active_injection.is_some()`), and OR in the later signals — don't rely on a single phase marker to stand in for the lifecycle.
- When a fix must apply at several call sites in a loop, extracting a named predicate first is what makes the fix verifiable at all. (The same widened condition was needed at two places (`/exit` scan, continuity buffer). Inlining would have duplicated it inside an async select loop that is impractical to unit-test.) - Reach for the pure-predicate extraction before editing the call sites, then write the truth-table test — the pattern already exists in this file as `injection_pop_allowed`.
- Suppression fixes trade a false positive for a false negative, and that trade should be stated where it lands. (With the wider guard, a genuine agent-issued `/exit` or continuity header emitted while an injection is in flight is silently dropped.) - Confirm the suppression window is bounded by injection completion (not by a timeout or an error path that could leave `active_injection` set indefinitely) — a stuck injection would permanently deafen command detection.
