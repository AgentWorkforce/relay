# Moving the probe core into relay

The Agent Relay desktop "probe" is the native Rust core that discovers
running coding-agent sessions and injects Relay messages into them through
each harness's native route (Claude Code, Codex, Devin, OpenCode, Grok, Pi,
Cursor CLI, OpenClaw, Hermes, Muse). It lived in relay-desktop next to the
apps. This note covers moving **only the core** into relay as `crates/probe`,
so the relay CLI can install and run it headless and injection works without
the desktop GUI. relay 15.0.0 is held until injection works through the probe.

## Decisions

- Only the core moves. The macOS, GTK (Linux and Windows) and iPad apps stay
  in relay-desktop and consume the core from relay.
- **Clean snapshot, no history.** relay is public, and relay-desktop's history
  holds documents and a PostHog key that were later scrubbed. Phase 1 imports
  the tree at relay-desktop `origin/main` as new files only.
- **Own Cargo workspace.** `crates/probe` has its own `[workspace]` and
  `Cargo.lock`. It does not join the root (broker) workspace yet, because the
  two pin conflicting `relaycast` (10 vs 9), `nix` (=0.25.1 vs 0.30) and
  `portable-pty` (=0.8.1 vs 0.8) versions.

## Version stamping

`build.rs` no longer reads relay-desktop's `CHANGELOG.md`:

- `AGENT_RELAY_PROBE_VERSION=X` stamps exactly `X`. Releases already pass
  this. relay-desktop's `build-probe.sh`, `build-linux.sh`,
  `build-windows.sh` and `desktop-release.yml` pass the desktop CalVer, and
  a relay release would pass the relay version.
- Otherwise, a development build is `<base>-dev+<git revision>`. The base is
  `AGENT_RELAY_PROBE_BASE_VERSION` when set: relay-desktop should pass its
  newest CalVer, which it used to read from its changelog, so development
  cores still order below the next desktop release. Without it, the base is
  the crate version (`0.1.0`).

## CI

`.github/workflows/probe-ci.yml` runs only for `crates/probe/**` (and its own
file). It runs:

- a Linux x64 build and test, with an empty `HOME`;
- a Linux x64 build and test of the core without history (`core-only`, see
  phase 1.5), with the dependency-tree and contract checks;
- a macOS arm64 build and test, and a build without history;
- a Windows x64 build (MSVC), with and without history;
- the contract-drift check (`generate-contract.sh`, then `git diff
--exit-code`);
- the public-source check.

PR runs cancel superseded runs, and other runs get per-SHA groups (the
relay#2010 pattern). Actions are pinned to the SHAs relay already uses.

relay-desktop CI checks that are not ported yet:

- `rust-oleum` (the config moved and was pruned of GUI entries);
- the glibc 2.34 floor;
- arm64 Linux, x64 macOS and arm64 Windows lanes;
- the Pi live-session scripts.

## Phase 1.5: the core without relayhistory

relay must not depend on relayhistory, and relay and relay-desktop must be
able to share one core. Session history, meaning local capture and upload to
RelayHistory, is the only part of the crate built on relayhistory (`ai-hist`
and `history-provider-sources`). It is now behind a `history` Cargo feature,
on by default:

- **relay** ships `--no-default-features --features production-binaries`.
  That build has no `ai-hist`, `history-provider-sources` or `notify` in its
  dependency tree, and CI fails if they come back.
- **relay-desktop** builds with the default features (`history` on) and gets
  exactly what it has today. The default build's behaviour is unchanged.

### What is in each build

Without `history` the core is the messaging runtime: `relay serve`
(discovery, native delivery and injection per harness, harness setup and
hooks, Relaycast and the workspace, spawning, the bridge and its contract,
launch at login), `relay call`, `connect` and the install helpers.

Only the `history` build has:

| Gated                                                                                                                              | What it is                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `delivery`, `destination`, `retention`                                                                                             | The upload queue, the RelayHistory receiver and history retention                           |
| `relay::session_query` (and the uploader's catalog search)                                                                         | `uploader.sessions.query`/`.facets` over `history.db`                                       |
| The uploader's background monitor and history reader                                                                               | Reads `history.db` directly                                                                 |
| `relay::history_retention`'s store                                                                                                 | Saves the retention policy in RelayHistory's store                                          |
| `relay::devin_cloud`, `relay::claude_web` catalog reads and the Devin Cloud send                                                   | The remote sessions come from the history catalog and `history-provider-sources` connectors |
| Hermes title roots (`session_titles::extra`)                                                                                       | `ai-hist`'s provider-root resolver                                                          |
| `cloud::devin_credential` and the auth-refresh send path                                                                           | Used only by uploads and the Devin connector                                                |
| The binary's history commands (`cloud`, `run`, `start`, `stop`, `status`, `installs`, `sessions`, `sharing`, `history flush`, ...) | The collector, which the uploader runs as child processes                                   |
| 9 integration tests and the `native_visibility_host` example                                                                       | History tests (`required-features = ["history"]`)                                           |

Moved so both builds share them: the pure delivery stall rules
(`delivery_status`) and the binary's JSON output helpers
(`src/probe/output.rs`). `HISTORY_VERSION` exists only with `history`;
`history_version()` returns `None` without it.

### The bridge without history

The contract does not change with the feature. It is generated from the
method registry, which no `cfg` touches, so both builds generate the same
`CoreContract.swift`; the `contract` job checks the history build against the
checked-in file and the `core-only` job checks the no-history build against
it too. The apps need no per-build contract.

Without `history`:

- The history-only methods, `relay::contract::HISTORY_METHODS` (every
  `uploader.*` method and `sessions.transcript`), answer the new error kind
  `history_unavailable` (code -32000, not retryable) with "Session history is
  not available in this build of the Agent Relay core." The server refuses
  them before reading their parameters. The generated Swift call for each
  says so, and `hello` still lists them.
- `settings.set` of `history_retention_days` answers `history_unavailable`
  before anything is written, so no other setting in the same batch is
  saved; `settings.get` reports the default, 30.
- `status.get` reports `daemon.history_version` as null.
- **Devin Cloud delivery is history-only.** Devin Cloud and claude.ai web
  sessions are not discovered, and nothing is sent to Devin Cloud. A send
  to a cloud-shaped id keeps the local answer (`Waiting` while no local
  Devin session holds it), since a stopped local session can have that id
  shape, as a history build does when no Devin sign-in can carry the send.
- The uploader runs no child process: it finds no install, reclaims nothing,
  and refuses every other command with `history_unavailable`. Cloud sign-in
  (`account.sign_in`) adopts the workspace for messaging, then ends in
  `error` with that sentence, because its last step is the uploader's
  `cloud install`. relay resolves its workspace from the CLI (phase 2,
  below), not from a Cloud sign-in.
- Agent-led setup on the relay-send socket (`/setup/*`) does not wait for
  an uploader: its bootstrap closes once direct delivery and automatic
  activation are set, and `POST /setup/sharing` answers `setup_unavailable`
  (503), as a core without the account methods does.
- Hermes session titles are not editable.

### Next step

This is a feature, not yet two crates, so it stays reviewable. The next step
moves the gated code into its own crate (for example `agent-relay-history`,
depending on the core and `ai-hist`), hooked into the core through traits in
place of the `cfg` seams. relay-desktop would then depend on both crates. The
seams mark where those traits go:

- session catalog search;
- history retention;
- the remote-session source and sender (Devin Cloud, claude.ai);
- the uploader's runner (`ProbeRunner`: `ProcessRunner` with history,
  `NoHistoryRunner` without) and history reader.

## Phase 2: the probe reads the CLI's workspace (done)

`src/relay/workspace.rs` now resolves the daemon's one Relaycast workspace
from two sources, read-only (the probe never writes the CLI's files):

1. **The `agent-relay` CLI** (`src/relay/workspace/cli.rs`), mirroring
   `packages/cloud/src/project-workspace-key.ts` `resolveWorkspaceSelection`
   and `packages/cli/src/cli/lib/sdk-client.ts` `resolveWorkspaceTransport`
   (minus the `--workspace-key` flag):
   1. the env key: `RELAY_WORKSPACE_KEY` > `AGENT_RELAY_WORKSPACE_KEY` >
      `RELAY_API_KEY`;
   2. the project pin `<project>/.agentworkforce/relay/workspace-key.json`,
      only when `AGENT_RELAY_PROJECT` names the project (the CLI's explicit
      project root; the daemon has no working directory to search from). A
      missing or malformed pin falls through, as in the CLI. Persisted
      Relaycast routes (`relaycastRoute`/`relaycastBaseUrl`, and the route
      credential `relaycastApiKeyRef` names in `relaycast-credentials.json`)
      are honoured with the CLI's checks;
   3. the active entry of `$AGENT_RELAY_HOME|~/.agentworkforce/relay/workspaces.json`.

   Origin: a persisted route (Agent Relay gateways only; a key bound
   elsewhere is refused), else `RELAY_BASE_URL`, else the key's binding in
   `relaycast-origins.json` (`src/relay/workspace/origin_binding.rs`:
   PBKDF2-HMAC-SHA256, salt `agent-relay:relaycast-origin-binding`, 10,000
   iterations, 16 bytes hex, via the `ring` already linked; tested against
   `packages/contracts/fixtures/relaycast-origin-binding.json`, the vector the
   CLI and the broker use), else armadillo for an `ar_ws_…` key, else
   `https://cast.agentrelay.com`. A bound key
   goes only to its server; `http://127.0.0.1:8787` and other self-hosted
   http(s) base URLs (ports and path prefixes included) are accepted as the
   CLI accepts them. A malformed bindings file, an unreadable `workspaces.json`
   or a malformed `RELAY_BASE_URL` fails closed.

2. **The Cloud sign-in** (`cloud` in the agent store; `RELAYCAST_URL` still
   re-origins only this key), used only when the CLI names nothing.

**Combination rule.** The CLI source wins whenever it names a workspace, so
the probe registers and injects in the same workspace the CLI's MCP tools in
each session use; within the CLI source an explicit env key or project pin
outranks the machine store, exactly as in the CLI. The Cloud sign-in is the
fallback for desktop users who never ran the CLI. A CLI selection that may not
be used (fail-closed cases above) leaves the daemon with **no** workspace and
an activity warning: it never falls back to the account's workspace, and
neither source's key is ever sent to the other's origin. `Workspace.source`
records which source named the key.

**Refresh, verification and recovery.** The 30 s rediscovery re-reads the
CLI's files, so a key rotated in `workspaces.json` is picked up and verified
by the next pass (and the existing same-origin key-migration bookkeeping
applies). Cloud recovery (`account/workspace_recovery.rs`) runs only for a
`Cloud`-sourced key; a refused CLI key is left `rejected` until the CLI's
files change.

**One workspace per daemon.** The daemon holds a single
`Mutex<Option<Workspace>>` that about 40 call sites (registrations, push,
delivery, spawn, messaging, verification) read as _the_ workspace, so this
phase supports one workspace per machine: the env key, the
`AGENT_RELAY_PROJECT` pin, or the machine's active CLI workspace, else the
Cloud sign-in. A project whose pin names a different workspace than the
machine's active one is **not** served by the daemon yet; that needs per-
registration workspaces (a registration already records its `base_url` and
`workspace_key`, but discovery, push and verification assume one). Until
then, `relay init` keeps the machine-wide active workspace (#2007), so the
common single-workspace machine is covered.

Behaviour change for desktop users: a desktop that is signed in to Cloud
**and** has an active CLI workspace now uses the CLI's for messaging (uploads
still go to the signed-in account). This lands in relay-desktop only when it
consumes this core (phase 4).

## Phase 3: `relay init` installs and runs the core (done)

`relay init` now injects messages into running sessions through the core
instead of adding the Relay MCP server (`packages/cli/src/cli/commands/init.ts`,
`packages/cli/src/cli/lib/probe-core.ts`).

**Release artifacts.** `.github/workflows/probe-release.yml` builds
`agent-relay-probe` with `AGENT_RELAY_PROBE_VERSION=<version>` for
linux-x64 and linux-arm64 (glibc, Ubuntu 22.04 runners), darwin-arm64,
darwin-x64 (cross-compiled on Apple silicon, not smoke-tested) and
windows-x64, checks that each binary reports `agent-relay-probe <version>`,
and publishes it with a `.sha256` sidecar (`<hex>  <asset>`):

```text
probe-v<version>/agent-relay-probe-<version>-<os>-<arch>[.exe]
probe-v<version>/agent-relay-probe-<version>-<os>-<arch>[.exe].sha256
```

`probe-v*` tags never collide with the CLI's `v*` tags, and the release is
created with `--latest=false` because `install.sh` resolves the CLI through
`releases/latest`. The workflow is `workflow_dispatch` only (inputs `version`,
`dry_run`, which defaults to true and builds without tagging), plus a dry run
on pull requests that change the workflow. No release has been cut: the CLI
pins `PROBE_VERSION = '15.0.0'`, so `probe-v15.0.0` must be released before
relay 15.0.0 ships, or `relay init` falls back to the MCP server.

**Install.** The CLI downloads the pinned asset into the canonical bin
directory (`$AGENT_RELAY_INSTALL_DIR/bin`, else `$AGENT_RELAY_HOME/bin`, else
`~/.agentworkforce/relay/bin`; `getCanonicalProbePath` in
`@agent-relay/harness-driver/install-paths`) exactly as it installs
`relaycast-engine` (`ensureReleaseBinary`): checksum first, SHA-256 verified,
written to a temp file beside the target, run with `--version`, then renamed
into place atomically. A binary that already reports the pinned version or a
newer one is kept; `AGENT_RELAY_PROBE_PATH` names a binary to use instead.
There is no musl, arm64 Windows or 32-bit build. When a download or update
fails, init uses the binary already in the bin slot if there is one; the MCP
server is the fallback only when no core answers and no usable core binary
is there to start (those machines included).

**One core per machine (the attach rule).** Before installing anything, init
connects to the core's bridge socket (`AGENT_RELAY_CORE_SOCKET`, else
`~/.agentworkforce/desktop/core.sock`; on Windows the named pipe derived from
it, a vector shared with `relay::transport`'s tests). It refuses a socket in a
directory another user can write to, greets with `hello` (bridge version 2)
and reads `status.get`. A core that answers is used: the desktop app's
service, a systemd unit, or the one an earlier `relay init` started (told
apart by the pid in `<relay home>/local/core.json`). Only when nothing answers
does init start `agent-relay-probe relay serve --headless --cli-managed
--socket <socket>` detached (log `<relay home>/local/core.log`) and wait up
to 30 s for it; the core's own `flock` on `core.sock.lock` settles a race, and
init then attaches to the winner. Re-running init reuses the running core.
`relay init --stop` stops only the core whose pid init recorded and that
still answers on the socket with that pid (through `daemon.shutdown`, SIGTERM
as a fallback), never the desktop app's; a recorded core that no longer
answers is never signalled, since its pid may have been reused, and its
record is dropped. Init speaks only to a socket owned by the user with mode
0600 in a directory only the user can write to, whose `hello` names a bridge
version and pid (Node cannot read peer credentials; the core itself admits
only this user's peers).
`agent-relay-probe relay call status.get` shows which core runs.

`--cli-managed` (new, requires `--headless`) is headless without the parts
that belong to the desktop's service: it keeps the desktop app's login entry,
and the core turns on nothing by itself, neither the agent-led defaults at
start nor the integration defaults of each refresh pass
(`apply_integration_defaults`), so every per-user file it edits is one the
person chose in `relay init`.

**Hooks or MCP, per tool.** Each injected tool gets the core's own delivery
route and no MCP server, so a session has exactly one Relay identity: the one
the core registers. Init turns on `auto_activate` (sessions join on their
own, named `<tool>-<project>-<task>`) and, per tool, through `settings.set`:

| Tool        | Core setting(s)                                  | What the core writes                                                                                                                          |
| ----------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `direct_delivery_default`, `claude_session_hook` | `crossSessionInbound: "accept"` (only when unset), a SessionStart hook and `permissions.allow` rules in `~/.claude/settings.json`             |
| Codex       | `codex_stop_hook`                                | PostToolUse, Stop and SessionStart hooks in `~/.codex/hooks.json`, trusted through Codex's app-server, and `~/.codex/rules/agent-relay.rules` |
| OpenCode    | `opencode_plugin`, `opencode_auto_activate`      | the Agent Relay plugin under `~/.config/opencode/plugins`                                                                                     |
| Grok CLI    | `grok_leader`                                    | `[cli] use_leader` in `~/.grok/config.toml`                                                                                                   |
| Devin       | `devin_direct_delivery`                          | lifecycle hooks in `~/.config/devin/config.json`                                                                                              |
| Cursor      | `cursor_direct_delivery`                         | hooks in `~/.cursor/hooks.json` (the editor route needs a core newer than 15.0.7)                                                             |
| Pi          | `pi_extension`, `pi_auto_activate`               | the Agent Relay extension in `~/.pi/agent/extensions` (a desktop core installs it at start)                                                   |

`auto_activate` alone never puts an open Pi or OpenCode session on the relay
(the desktop installs both routes by default, so its Auto-activate switch
keeps them joining only when added). `pi_auto_activate` and
`opencode_auto_activate`, off unless turned on, let those sessions join by
themselves while `auto_activate` is on; init turns on the one for each tool
chosen, and they are recorded and undone like the rest.

A setting that is already on is left alone; the ones init turned on are
recorded in `<relay home>/local/core-settings.json`, and `relay init
--uninstall` (both scopes, or `--scope global`) turns off exactly those. The
core turns Claude's direct delivery off by writing `hold` on every Claude login
it follows, the person's own `accept` included. Before turning it on, init
records each login's `crossSessionInbound` (or its absence), and after every
turn-off (a rollback, a record it could not save, `--delivery mcp`,
`--uninstall`) puts those values back where the core left `hold`.

Each tool is on exactly one route. When one of a tool's settings fails, init
stops there, turns off what it had turned on for that tool, and gives it the
Relay MCP server; `auto_activate` is turned on only once a tool is injected,
and every tool gets the MCP server when the core cannot be had. When a
setting init turned on cannot be turned off again (after a failed tool, or
when the record cannot be saved), setup stops with that error and adds no
MCP server for it. `--delivery mcp` asks for the MCP server explicitly, and
first turns off the recorded settings of those tools (and `auto_activate`
once no injected tool is left); when that fails, no MCP server is added. An
MCP entry an earlier `relay init` added is removed for each injected tool, in
both scopes. The one case that can leave a tool on both routes is a removal
that fails (a read-only config, for example): init reports it with the file,
and the entry must be removed by hand.

These are settings of the user account, so they apply in every project
whatever `--scope` says; `--scope` now only places the MCP fallback, and the
guided flow no longer asks for it unless `--delivery mcp`. The earlier fixes
stay: no `_npx` paths or home paths in project files, the workspace key is
git-excluded, the active workspace is not switched, and Codex's project-trust
offer still applies to a project-scope MCP fallback.

The Claude SessionStart hook now knows automatic activation: a session that
is not registered yet but will be is told it joins by itself (with the
session socket's `/whoami`, `/agents` and `/send` commands) instead of being
told to ask the person whether to register, which raced auto-activation.

**Codex's sandbox.** Codex's default sandbox (`workspace-write` or
`read-only`, network off) denies every Unix-socket connect on macOS, so a
Codex session could not run `agent-relay-probe relay read` or its reply
`relay socket-request` without asking to leave the sandbox, and one went on to
answer through another Agent Relay connector it had ("Agent Relay in
ChatGPT"), as a different identity in another workspace. Codex has no
narrower grant for one socket in its ordinary sandbox settings
(`sandbox_workspace_write` offers only `writable_roots` and all-or-nothing
`network_access`; a Unix-socket allowlist exists only in permission profiles
and managed network policy, which replace the person's sandbox setup). Codex
does run a command outside its sandbox without asking when every part of it
matches an `allow` prefix rule in `~/.codex/rules/*.rules`. So while
`codex_stop_hook` is on, the core also writes
`~/.codex/rules/agent-relay.rules` (`agent-relay-dev.rules` for Agent Relay
Dev) with exactly two rules: `<this probe> relay socket-request --socket <this
core's session socket>` and `<this probe> relay read --socket <the same socket>` (the pointer a session is handed now names the socket, and `--socket` refuses `--dev`). Nothing else leaves the
sandbox and no network is granted; a rules file of that name that does not
start with Agent Relay's header is never touched, and the rules go to
`agent-relay-2.rules` (up to `-9`) instead; with every name taken, turning
the hook on fails. Reply hints are one command
with the body as `--body` (no `printf |` pipe, since every part of a command
must match a rule), and every reply hint ends with a `[route: …]` line telling
the agent to answer only that way, never through another Agent Relay
connector or app, and to say so if it fails.

**Fixed routes for Codex's rules.** A Codex prefix rule constrains only a
command's leading words, so the `relay socket-request --socket <socket>`
rule let anything after the socket through: a relayed (untrusted) message
could steer Codex into `--method PATCH --path /settings` or
`--method POST --path /register`, which ran with no prompt. The rules now
allow only the probe's self-limiting session commands, each with `--socket`
naming this core's session socket: `relay send` (`POST /send`, with `--to`,
`--address` or `--channel`, `--reply-to` and `--thread`), `relay agents`
(`GET /agents`), `relay whoami` (`GET /whoami`), `relay read`
(`GET /messages`), `relay fetch-attachment` (`POST /attachments/fetch`),
`relay connect-send` (`POST /connect/send`) and `relay subscribe-channel`
(`POST`, or with `--remove` `DELETE`, `/channels/subscribe`).
Each fixes its own method and route, checks every other argument (one name
or `agent@machine` address with no whitespace or URL characters, plain ids)
and percent-encodes it into the query, and clap refuses a repeated
`--socket`. Every hint a session is handed names these commands, and the
Claude rules allow the same ones. That includes the Claude SessionStart
preamble and joining text, which named curl and so asked in manual mode: the
core's `GET /setup/status` answer now carries `probe` (the space-free link
when it is in use), and the hook writes its commands through it. `relay socket-request` stays for people
and debugging, with no rule, so it asks. A test enumerates every route the
session socket serves (read from the router's source) and checks that no
argument list after any allowed prefix reaches one other than that rule's
own; another runs `codex execpolicy check` when Codex is installed. A core
that finds an older Agent Relay rules file (any name) rewrites or removes
it, so an upgrade leaves no `socket-request` rule behind.

Turning `codex_stop_hook` off puts `~/.codex` back: the hook's keys are listed
through Codex's app-server while the hook is still in `hooks.json`, the hook
comes out, then exactly those `hooks.state` entries leave `config.toml` (and
`[hooks.state]` / `[hooks]` once empty). A `hooks.json` the core created is
removed once empty; the person's own is restored byte for byte from the
`.relay-desktop-backup` copy (taken only of a file that did not already hold
the hook) when they have not changed it since, and the copy is removed. A
`config.toml` that trusting the hook created (recorded in the core's data as
`codex-config-created`) is removed once nothing else is in it. The rules file
goes, and `rules/` with it only when empty.

**Claude's permission prompts.** In Claude Code's default ("manual")
permission mode a session asked to approve the pointer's `relay read`, then
again for its curl reply. While `claude_session_hook` is on, the core adds
rules to `permissions.allow` in each login's `settings.json` it puts the hook
in, for exactly the commands a relayed message hands the session, each only
for this probe on this core's session socket (`<req>` is `<this probe> relay
socket-request --socket <this core's session socket>`):
`Bash(<this probe> relay read --socket <the same socket> *)`,
`Bash(<req> --method POST --path '/send?*)` (a DM or channel-thread reply),
`Bash(<req> --method POST --path '/connect/send?*)` (a Relay Connect reply),
`Bash(<req> --method POST --path '/attachments/fetch?file_id=*)` and
`Bash(<req> --method GET --path /agents)`. Every other session route
(`/register`, `PATCH /settings`, `/integrations/subscribe`, …) still asks, and
`relay socket-request` refuses a second `--socket`, `--method` or `--path`, so
nothing after a `*` can change them. The probe, socket and path are quoted
exactly as the hints quote them (a socket under `Application Support` is
single-quoted). Claude Code matches the
text before a rule's `*` as written, after splitting compound commands
(verified against Claude Code 2.1.314 in print mode: the hint's own spelling
runs without a prompt, a body with `;`, `&&` or `$(…)` inside single quotes
included; a double-quoted or backslash-escaped socket, another socket, a
chained `&& touch …`, a double-quoted `$(…)` body, `PATCH /settings`,
`POST /register` and `POST /integrations/subscribe` all still ask). So the
reply, `[agents: …]` and attachment hints a Claude session is handed are now
the probe's one-command `relay socket-request … --body` form on every
platform (curl only when the probe's path is unknown), as Codex's are. A
symlinked or space-free socket alias was not needed: the quoted path matches
reliably, and an alias would be one more path for the rules to name. The
rules Agent Relay added are recorded in the core's data
(`claude-permission-rules.json`), so turning the hook off takes out only
those: a rule the person had already, even the same one, stays. A moved app
or socket replaces only Agent Relay's own rules. Turning the hook off also
puts the file back: the person's `.relay-desktop-backup` copy (now taken only
of a file that did not already hold the hook) is restored byte for byte when
nothing else changed, and a file the hook created is removed once empty.

**A probe path with spaces.** Codex's rules match a command only when its
program is a plain, unquoted word (`shell-command/src/bash.rs` in Codex 0.163:
the command name must be a `word` node; quoted arguments, single or double,
are read as one word and match). The macOS app's probe is
`/Applications/Agent Relay.app/Contents/Helpers/Agent Relay Helper`, which the
hints must quote, so Codex asked for every read and reply even with the rules
in place. So while `codex_stop_hook` or `claude_session_hook` is on and the
probe's path needs quoting, the core keeps a link to it at
`~/.agentworkforce/desktop/bin/agent-relay-probe` (`agent-relay-probe-dev` for
Agent Relay Dev), and the Codex rules, the Claude rules, the pointers and every
reply hint (Codex, Claude Code, OpenCode, Grok) name the link. The socket keeps
its own, quoted path: Codex matches a quoted argument, so it needs no alias.
The link is pointed at the running probe again whenever a hook turns on and at
each core start, so a moved or updated app never leaves it at an old binary;
a probe that moved to a space-free path drops it. The core uses the link only
when its folder and that folder's parent are real folders this user owns that
nobody else may write (the folder is made `0700`), it is the link the core
recorded making (`probe-alias.json` in its data: name, target and the link's
inode), and it points at exactly the running probe. Anything else at that name,
including a link someone put in its place, is never replaced, removed or used,
and the hints and rules name the probe's own path as before; every hint checks
the link again. Once neither hook is on (turned off, or `relay init
--uninstall`), the link goes, with its folder once empty, and hints name the
probe's own path again; a hint handed out earlier that names the link no longer
runs (without the rules it would have asked anyway). The record also names the
link being replaced while the app moves, so a core stopped mid-move finishes
the move at its next start. The rules
still allow only the same two (Codex) and five (Claude) command shapes.

**`--uninstall` and the tools' own folders.** Before the core edits them,
init records each Claude login's `settings.json` (whether it, its
`.relay-desktop-backup` and its folder existed) and the OpenCode plugin's
place (whether `agent-relay.js`, its `.off` marker and `plugins/` existed).
Once nothing init turned on edits them any more, it tidies them back: a
Claude `settings.json` init created is removed once it is `{}` (with the
core's copy of it, and the folder when init made it and it is empty), a file
that existed comes back byte for byte from the core's copy when its content
is unchanged, and a file the person changed since, a linked file and a copy
from before init are left alone. The `.off` marker is the core's record that
the person turned the plugin off, so the desktop's on-by-default does not
put it back; init removes it (and an empty `plugins/` it created) only when
init installed the plugin where there was neither a plugin file nor a marker
before. A desktop core turning the plugin off still leaves the marker.

**Workspace.** The core serves one workspace per machine (phase 2). After
setting up, init calls `workspace.refresh` and warns when the core serves a
different workspace than the project's: the verified Relaycast workspace id
decides when both sides know it (one server can host many workspaces), and a
self-hosted setup whose id cannot be compared says so (for example a desktop signed in to
another workspace, or a machine-wide active workspace this project does not
use), with the `relay workspace switch` command that aligns them.

`relay init --hosted`, `--key` and `--url` make the new workspace active when
the active one is the `local` workspace of init's own server, or none, unless
a core init did not start is running: that core follows the active workspace
too, so it stays as it is and init warns. The core picks a switch up live on
`workspace.refresh`; a restart adds nothing. A session already on the relay
stays in the workspace it registered with (the store keeps that workspace's
key), so init also runs `agents.unregister` and `agents.register` for each
running agent whose id the local server confirms, under the same name. An agent
with an alias, a reply setting, a webhook, integrations or a spawner is left in
place and named, since a new registration drops that state, and so is one whose
session ended, which could not register again.

**Service.** `relay init` starts the core as a detached background process
and installs no service; when it is not running, `relay init` starts it
again. For an always-on core, install the desktop app (its systemd unit or LaunchAgent), or run the
core as a user service yourself, for example:

```ini
# ~/.config/systemd/user/agent-relay-core.service
[Unit]
Description=Agent Relay core
[Service]
ExecStart=%h/.agentworkforce/relay/bin/agent-relay-probe relay serve --headless --cli-managed
Restart=on-failure
UMask=0077
[Install]
WantedBy=default.target
```

`relay init` attaches to it like any other running core.

**End-to-end proof** (Linux, Claude Code 2.1.280, Codex 0.154.0; isolated
`HOME`, `XDG_*`, `AGENT_RELAY_HOME`, `AGENT_RELAY_INSTALL_DIR`, socket and
app data, with a throwaway git project): `relay init --tools claude,codex`
started the core; an interactive Claude Code session in tmux joined by
itself; `relay message dm send … --as alice` was injected into the live
session as a turn three seconds later (no inbox call), and its reply reached
alice. Claude then messaged the Codex session over the session socket; the
message was injected into the idle Codex TUI through Codex's queue, and
Codex's reply was injected back into Claude. A core started outside init (as
the desktop's would be) was attached to, not doubled, and survived `relay
init --stop`; `relay init --uninstall` turned the four settings back off.

## Remaining phases

4. **relay-desktop consumes the core from relay**, as a Rust crate pinned to a
   relay commit, the way it consumes relayhistory, with one core per machine
   (see below). The attach rule above already makes `relay init` use the
   desktop's running core. This first needs step 2b of "Until the switch".
5. **Per-project workspaces.** The core still serves one workspace per
   machine; a project pinned to another workspace is warned about, not
   served. That needs per-registration workspaces in the core.
6. **`AGENT_RELAY_PROJECT` inference.** The daemon has no working directory,
   so it uses a project's pin only when `AGENT_RELAY_PROJECT` is in its
   environment; the core could infer the project from each session's `cwd`.

Known gaps in phase 3:

- Messages arrive as pointers (`show_relay_messages` off, the core's default):
  the session runs `agent-relay-probe relay read --socket <socket> <ref>` for the text.
- `--uninstall` leaves the one-time `.relay-desktop-backup` copies of edited
  settings files other than Codex's `hooks.json` and Claude's `settings.json`
  (see "Codex's sandbox" and "Claude's permission prompts" above for what
  those get back).
  A `--cli-managed` core writes into `~/.pi` only when `pi_extension` is
  turned on; turning it off removes only Agent Relay's own extension file and
  records the choice in the core's data (`~/.agentworkforce/desktop/pi-extension.off`).
- The core's own telemetry (its `analytics_enabled` setting, on by default)
  does not follow the CLI's opt-out (`AGENT_RELAY_TELEMETRY_DISABLED`); turn
  it off with `agent-relay-probe relay call settings.set --params
'{"analytics_enabled":false}'`.
- relay-desktop CI lanes still not ported (above): glibc floor check, arm64
  Linux tests, x64 macOS and arm64 Windows lanes.

## Until the switch: two cores

relay's `crates/probe` is the relay-desktop core at `5601b739`
(2026-10-28). Both copies kept changing after that:

- relay-desktop's `probe/` has gained about 39 merges. Among them are the
  OMP harness, Windows agent-led setup, spawn approvals, plan limits, Claude
  session attestation, auth health and the Claude plugin push.
- Those merges add bridge methods (`account.mcp_headers`, `agents.end`,
  `tools.*`) and contract fields that the macOS and GTK apps use and relay's
  core lacks.
- relay's copy has the CLI work: phases 1.5 to 3, and the `relay init`
  fixes for Codex's sandbox, Claude's permission prompts, the space-free
  probe link and uninstall cleanup.

So relay-desktop cannot build relay's core today: the apps would not compile,
and desktop features would disappear. Until it can:

1. **Duplicate fixes desktop users need.** A core fix in relay that changes
   desktop behaviour is ported to relay-desktop's `probe/` as well, staying as
   close to relay's code as desktop's newer code allows. The first port carries
   the Codex sandbox route and rules, the Claude allow rules and the
   space-free probe link.
2. **Make relay the core's home.** The step that unblocks the switch:
   1. (2a) Freeze core edits in relay-desktop's `probe/`, and send new core
      work to relay.
   2. (2b) Port relay-desktop's core changes since `5601b739` into
      `crates/probe`, keeping relay's `install`/`session_model` split and the
      `history` feature. Then regenerate `contract/CoreContract.swift`, so that
      relay's contract is a superset of the desktop's.
3. **Switch.** relay-desktop depends on `agent-relay-probe` as a Rust crate,
   pinned to a relay commit, the way it depends on relayhistory. It uses a
   git dependency with `default-features = false` plus the features it needs,
   and builds the bundled binary from that same commit, so CalVer stamping,
   signing and notarization stay in the desktop build. The steps are below.

### The `relay-cli` feature

`crates/probe` builds the CLI's side of the core behind the `relay-cli` Cargo
feature. It is in `default`, and `production-binaries` implies it, so relay's
release command keeps it. It covers the CLI's workspace selection and origin
bindings, `ar_ws_`/`ar_ag_` keys, the CLI's `cloud-auth.json` sign-in and fleet
brokers. Without it the core reads only the Cloud sign-in, accepts only `rk_`
workspace keys, and `fleet.*` stay in the contract but answer
`method_not_found`. Secret scrubbing keeps the `ar_` prefixes in every build.
Cargo features merge across a dependency graph, so a consumer that must stay
without it has to assert that in its own build.

## What relay-desktop must change to consume the core

Phase 1 changes nothing in relay-desktop. Once relay's contract covers the
desktop's (step 2b above), relay-desktop must do the following to switch over:

1. Make the GTK app its own crate (for example `gtk-app/`) depending on
   `agent-relay-probe` from relay (a git dependency on
   `AgentWorkforce/relay` pinned to a tag or commit, `default-features =
false, features = ["history"]`, so it keeps session history). That crate takes `linux_app/`, the `agent-relay` and
   `agent-relay-fake-core` binaries, the four app tests, `resources/linux`,
   `resources/windows`, and the dependencies `gtk4`, `ksni`, `tray-icon`,
   `tauri-winrt-notification`, `zip` and `tar`.
2. In `linux_app.rs`, replace `mod install` with `pub use
agent_relay_probe::install;`. In `linux_app/models.rs`, delete the six
   moved modules and `pub use agent_relay_probe::session_model::*;` (keep
   `settings::origin`, which other models still use).
3. Delete `probe/src` (everything but the app) and build `agent-relay-probe`
   from relay's `crates/probe` with the default features (`history` on; the
   relay release binary is built without it). That is `scripts/build-probe.sh`,
   `build-linux.sh`, `build-windows.sh`, `package-{linux,macos}-probe.sh`
   and the Desktop Release workflow. Keep passing `AGENT_RELAY_PROBE_VERSION`
   and add `AGENT_RELAY_PROBE_BASE_VERSION` for development builds.
4. Get `CoreContract.swift` either by copying relay's
   `crates/probe/contract/CoreContract.swift` or by running
   `crates/probe/scripts/generate-contract.sh --app-root <relay-desktop>`.
   The generated header now names relay's script. The contract drift check
   becomes "the macOS copy equals the pinned relay core's".
5. Make the core's `shared/session-*.json` vectors canonical in relay, and
   have the Swift tests read relay's copy or sync from it.
6. In CI, drop the lanes now covered by relay's `probe-ci.yml` (Probe,
   linux-core, macos-core-tests). Keep the GTK, Swift, packaging and glibc
   lanes. Repoint `check-open-source.sh`'s license check (`probe/Cargo.toml`)
   at the app crate, and split `rust-oleum.toml` (the GUI entries move with
   the app).
7. Replace relay-desktop's `docs/relay-core.md` and
   `docs/agent-relay-probe.md` with pointers to `crates/probe/docs/`. The
   core's contract test now checks relay's copy.

Phase 3 adds, for one core per machine:

8. Take over from a core `relay init` started. That core runs
   `relay serve --headless --cli-managed` from `~/.agentworkforce/relay/bin`
   and holds `core.sock.lock`, so the desktop's systemd unit, logon task or
   LaunchAgent would exit with "already running for this socket" and restart
   in a loop. When its own core cannot take the lock, the desktop should read
   `status.get` and, if the running core is not its own build, retire it with
   `daemon.shutdown` (no handshake needed) and start its own, as the macOS
   headless core already yields to the app's LaunchAgent. `relay init`
   attaches to whichever core answers, so it needs no change for this.
9. Optionally stop bundling the core and install the `probe-v<version>`
   release asset instead (same names, same `.sha256` sidecars), so the CLI
   and the desktop run byte-identical cores.
