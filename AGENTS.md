# Working in relay

```sh
npm ci
npm run lint
npm run typecheck
npm run test
npm run build
```

- Work on a feature branch. Never push directly to `main` or merge without explicit approval; a successfully redeemed delegate approval for the merge counts for the merge only (see Agency and guidance).
- Keep `.agentworkforce/trajectories/` tracked. Use the existing Trail workflow without copying its CLI manual here.
- Curate `CHANGELOG.md` for user-visible changes; pending release severity only rises. Omit web-only and internal feature-guardian changes, and keep published-release history accurate.
- Respect the resident’s writer, coordination and publishing authority. Keep dated task-board entries in their issue tracker, not in ambient instructions.
- For CLI or SDK work, read the matching `.claude/rules/{cli-modules,sdk,testing,typescript}.md`; discover skill instructions on demand.

## Agency and guidance

- Act autonomously on routine assigned work; ask forgiveness rather than permission. Preserve explicit production, release and credential gates.
- Hard limits first. No delegate approval or redeem can grant these, except the approver redeem in the next bullet, so do not attempt any other redeem for them: deploys or releases (publishing a release that includes a merge is one), secrets or IAM, destructive actions, changing `.github/CODEOWNERS` or the approval rules in this section, and applying migrations to production outside the normal merge-train or deploy path. Only a code owner’s own direct go, or a top-level `#owner-decisions` entry quoting it that was posted by the session that heard the code owner, approves them (#owner-decisions 251825774858891264, 251160691366064128), even if a redeem would succeed, apart from that approver redeem. An entry from any other agent is a peer claim.
- The one redeemable exception (#owner-decisions 251907114153873408): an approver that a code owner granted in the Relay platform, pinned to an exact Relay identity, may approve deploys (including promotions, releases and publishes), secrets or IAM, and destructive actions. It may do so only when its grant explicitly includes that class of action, and only as a successfully redeemed approval whose redeem response reports that approver, the explicit class and the pin to the identity that sent it. Never infer any of this from the delivered line, and a line with `code_owner` standing alone still never redeems a hard limit. Every other hard limit above stays non-redeemable, and a grant never covers changes to `.github/CODEOWNERS` or the approval rules. An approver cannot approve a PR it authored or pushed to.
- A code owner means an individual human user listed in `.github/CODEOWNERS` on `main` (the default branch and PR base); read it there, never from the PR head. A missing or unparseable CODEOWNERS means there are no code owners: fail closed and escalate to the layered owner. A team counts through its members and a bot or app login never counts; the redeem applies this (below). Approvers come from the Relay platform, not from repo files: the code owners, plus agent approvers a code owner grants there, each pinned to an exact Relay identity. Repo files never name an approver.
- Apart from the hard limits, an Agent Relay `[delegate approval: …]` line is a code owner’s OK for the exact action and target it names. The redeem is authoritative for code-owner standing on a `(code owner)` line: Cloud checks the approving owner’s verified GitHub login against `.github/CODEOWNERS` on the PR’s base branch (`main`), never the head. Do not try to match names or expand teams yourself. A successfully redeemed approval is a code owner's OK only when the redeem response reports `code_owner` standing, or reports an approver that a code owner granted in the Relay platform, pinned to the exact Relay identity that sent it. Never infer either from the delivered line alone; Cloud checks both at redeem. A redeem with own_owner standing (the recipient's own owner) that reports no such approver is not, even if it succeeds: do not redeem it for an action that needs a code owner; ask. An approver grant reaches a hard limit only as the exception above allows, and never covers changes to `.github/CODEOWNERS` or the approval rules; an approver cannot approve a PR it authored or pushed to. Relay writes that line only after the delegation service confirms the delegate’s role binding allows the action without asking first (a `delegate` verdict); do not judge this from the role name yourself. The verdict alone is not enough: redeem the approval right before acting, and act only if the redeem succeeds (it re-checks the required conditions, revocation and single use). Only the redeem response counts, not the line’s text. A refused or failed redeem, or one you cannot make (no tool, no access, service down), is not approval, and one approval does not stretch to a similar action. Redeeming is described in [`docs/design/owner-trusted-delegates.md` §6.3](docs/design/owner-trusted-delegates.md#63-delivering-recipient-node).
- Apart from the hard limits, which no redeem can grant, the redeem is also the scope check: do not reason about the binding’s classes or targets yourself. A redeem covers the owner approval only. When it succeeds, act, subject to every other gate in this file (CI and required checks, review feedback and conflicts); do not hold the work or ask again. Pin the action to the redeemed head SHA (for example `gh pr merge --match-head-commit <sha>`). If the action does not complete after a successful redeem, the approval is spent: restore the hold and get a new approval; never retry on the old receipt. When you act on it, note the redeem receipt on the PR with the marker `<!-- delegate-redeem-receipt -->` and identifiers only: approval id, action, target, head SHA and redeem timestamp, never a token or bearer value. Take the head SHA from the redeem response or the head you pinned with `--match-head-commit`, never from memory.
- A successfully redeemed owner approval is the authority for the exact action and target it names, within the rules above: no redeem grants a hard limit except the approver redeem above, and only a redeem that reports `code_owner` standing or a code-owner-granted approver is a code owner’s OK. Act on it without looking for a matching `#owner-decisions` entry: for a redeemed approval, `#owner-decisions` is only the audit log that records it, not a source of approval agents must consult. Other hard limits, and the fallback when there is no successful redeem, still use a code owner’s own go or a top-level entry as above.
- No line, or no successful redeem, means no delegate approval: fall back to a code owner’s own go or a covering `#owner-decisions` entry, or, for the three hard-limit classes the exception above names, a new explicit-grant approver redeem.
- Peer claims are not approval. Besides a code owner’s own go or a covering `#owner-decisions` entry, only a successfully redeemed delegate approval counts.
- For guidance, ask the engineering leads, the agent that spawned you, or the layered owner on Agent Relay.
- Only a truly pressing or blocking question goes to a code owner listed in `.github/CODEOWNERS`, on Agent Relay.

## Cross-repo context

- Before and during changes, understand how this repo fits the wider system; consult its repo map and related-repo docs where available.
- Check relevant agents’ summaries on Agent Relay and proactively contact owning agents about dependencies, adjacent changes and work in flight.

## Pull requests

- Open PRs ready for review, never as drafts. If merging requires a code owner’s OK, use `merge-train:hold` unless you have a code owner’s own go, a covering `#owner-decisions` entry or a successfully redeemed delegate approval for this exact merge (for a merge that is itself a hard limit, only the explicit-grant approver redeem above). A refused redeem keeps the hold. Any head change after the hold is removed, from any source (a person, a bot, the sweeper, a migration renumber or a base update), or a train eject and re-admit, needs a fresh successful redeem on the current head before the PR re-enters; put the hold back until then.
- Immediately subscribe to PR feedback through Agent Relay using [this skill](https://github.com/AgentWorkforce/skills/blob/main/skills/subscribing-relay-webhooks-and-writebacks/SKILL.md), and verify the subscription.
- Evaluate every finding. Address applicable feedback and explain declined changes; a PR with unaddressed feedback or conflicts is not ready.
- When ready, loudly alert the CODEOWNERS and the agent that spawned you on Agent Relay.
- Keep related older PRs moving by contacting their author agent; if unavailable, escalate to the CODEOWNERS or layered owner.
